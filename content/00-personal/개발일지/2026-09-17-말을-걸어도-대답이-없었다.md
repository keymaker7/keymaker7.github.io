# 말을 걸어도 대답이 없었다

"애들이 왜 응답이 없지?"

내 컴퓨터에는 늘 켜져 있는 도우미 프로그램이 아홉 개 있다. 말을 걸면 답하는 것들이다.
그런데 며칠째 조용했다.

## 💤 1. 살아는 있었다

먼저 켜져 있는지부터 봤다. 아홉 개 전부 돌고 있었다. 사흘 동안 한 번도 안 꺼졌다.
건강 상태를 물어보는 주소로 찔러보니 전부 "괜찮다"고 답했다.

```bash
curl -s http://127.0.0.1:<포트>/health
# {"ok":true,"status":"live"}
```

그런데 **일한 흔적이 12일 전에서 멈춰 있었다.**

살아 있지만 일을 안 하는 상태. 숨은 쉬는데 말은 안 하는 것과 같다.
"켜져 있다"와 "일하고 있다"는 완전히 다른 질문이라는 걸 다시 배웠다.

## 🕳️ 2. 오류를 통째로 버리고 있었다

로그를 아무리 뒤져도 왜 조용한지 안 나왔다. 이상했다.
프로그램이 죽을 만큼 문제가 있으면 뭐라도 남아야 한다.

시동 설정을 열어봤더니 이렇게 돼 있었다.

```xml
<key>StandardOutPath</key>  <string>.../gateway.log</string>
<key>StandardErrorPath</key><string>/dev/null</string>
```

**오류만 골라서 쓰레기통으로 보내고 있었다.** `/dev/null`은 "버려라"라는 뜻이다.
평소 이야기는 다 적고, 비명만 안 적고 있었던 셈이다.

여덟 개를 전부 파일로 돌렸다. 그리고 다시 켰다.

바꾸자마자 **10초 만에** 그동안 버려지던 오류들이 쏟아졌다. 아래 두 가지는 거기서 나왔다.

## 🔑 3. 열쇠가 거절당하고 있었다

둘은 접속 자체가 막혀 있었다. 메시지는 짧았다.

```
Discord API /gateway/bot failed (401)
```

`401`은 "너 누군지 모르겠다"는 뜻이다. 열쇠가 만료됐거나 바뀐 것이다.

이 메시지는 **몇 주 내내 나오고 있었다.** 다만 아무도 못 봤을 뿐이다.
버리라고 해둔 곳으로 계속 가고 있었으니까.

## 🎭 4. 둘이 같은 이름표를 달고 있었다

다른 하나는 더 이상했다. 켜면 접속은 되는데 금방 끊기고, 다시 붙고, 또 끊겼다.
8월 하순 기록을 보니 열 번 재시도하다 포기한 흔적이 있었다.

접속 기록에서 이름을 맞춰봤더니 답이 나왔다.

```
A 프로그램 → 접속 이름 @같은이름  (계정번호 1487...011)
B 프로그램 → 접속 이름 @같은이름  (계정번호 1487...011)
```

**두 프로그램이 한 계정을 나눠 쓰고 있었다.**
그 서비스는 계정 하나당 자리가 하나다. 둘이 켜지면 서로 밀어낸다.
번갈아 쫓겨나느라 아무도 제대로 못 앉아 있었던 것이다.

켜보고 알았으니, **바로 도로 껐다.** 그대로 두면 멀쩡히 일하던 쪽까지 흔들린다.
고치려다 멀쩡한 걸 망가뜨리는 게 제일 나쁘다.

## 🙈 5. 그리고 내가 아홉을 전부 내려버렸다

설정을 바꿨으면 다시 등록해야 반영된다. 내리고, 올리고. 아홉 번 반복하는 일이다.
나는 이렇게 썼다.

```bash
launchctl bootout  gui/501/$L >/dev/null 2>&1   # 내리고
launchctl bootstrap gui/501 "$P" >/dev/null 2>&1 # 올리고
```

내리는 데 시간이 조금 걸리는데, 나는 바로 올리라고 시켰다.
아직 내려가는 중이라 올리기가 실패했다. **그리고 그 실패를 `2>&1`로 숨겼다.**

결과를 확인해보니 아홉 중 여덟이 사라져 있었다. 내가 전부 내린 것이다.

웃긴 건, 30분 전에 내가 고친 문제가 **"오류를 안 보이게 버리는 것"**이었다는 점이다.
그걸 고치는 명령어에서 똑같은 짓을 했다.

다시 올리는 건 어렵지 않았다. 확인될 때까지 반복하게 만들면 된다.

```bash
until launchctl list | grep -q "$L"; do
  launchctl bootstrap gui/501 "$P"   # 숨기지 않는다
  sleep 2
done
```

## 🚪 6. 그리고 진짜 이유는 따로 있었다

여기까지 고치고 나서, 처음 질문으로 돌아갔다. "불렀는데 답이 없다."

접속 기록을 보니 이 친구들이 **듣고 있는 방이 따로 있었다.**
부른 쪽은 A방인데, 듣는 쪽은 B방이었다.

고장이 아니었다. 애초에 그 방에 없었던 것이다.

세 시간을 고쳤는데, 처음 증상의 원인은 이거 하나였다.
**"안 된다"는 말에서 출발하면 이렇게 된다.** 어디서 안 되는지를 먼저 물었어야 했다.

## 🧾 오늘 한 것

- 상주 도우미 아홉 개 상태 점검 — 전부 살아 있었으나 12일째 무작업
- 오류 버리던 설정 8개 수정, 원본은 백업
- 숨어 있던 문제 2건 발견 — 접속 열쇠 만료, 계정 중복 사용
- 잠들어 있던 둘 되살리고, 충돌하던 하나는 끄는 것으로 확정
- 각자 듣고 있는 방 목록을 정리해 기록

## 👨‍🏫 오늘 코딩선배의 가르침

### 1. "켜져 있다"와 "일하고 있다"는 다른 질문이다

프로그램이 돌고 있는지 보는 건 쉽다. 그런데 돌기만 하고 아무 일도 안 할 수 있다.
오늘 아홉 개가 전부 "괜찮다"고 답했지만, 12일 동안 아무것도 안 했다.

**살아 있는지는 숨으로 보고, 일하는지는 결과물로 본다.**
마지막으로 뭔가를 만든 게 언제인지 — 그게 진짜 확인이다.

### 2. 오류를 버리라고 해두면, 정말 버려진다

`/dev/null`은 컴퓨터에서 "쓰레기통"이다. 여기로 보내면 흔적도 안 남는다.

```xml
<string>/dev/null</string>   <!-- 비명 소리를 껐다 -->
```

몇 주 동안 "열쇠가 안 맞는다"고 계속 소리치고 있었는데 아무도 못 들었다.
**안 들리는 것과 문제가 없는 것은 다르다.** 시끄러운 게 조용한 것보다 낫다.

### 3. 고치려다 멀쩡한 걸 망가뜨리지 않기

한 명을 살리려고 켰더니, 옆에서 잘 일하던 친구가 흔들리기 시작했다.
바로 도로 껐다. **하나를 못 고치는 것보다, 되던 걸 망가뜨리는 게 더 나쁘다.**

되돌릴 수 있게 해두는 게 먼저다. 나는 바꾸기 전에 원래 설정을 복사해뒀다.
그래서 마음 놓고 켜볼 수 있었다.

### 4. 숨기고 실행하면, 실패한 줄도 모른다

명령어 뒤에 붙는 `2>&1`은 "화면에 아무것도 띄우지 마"라는 뜻이다.
깔끔해 보여서 자주 쓰는데, 오늘 그것 때문에 여덟 개를 날렸다.

- 나쁜 방법: 시키고 → 조용하니까 → 됐겠거니
- 좋은 방법: 시키고 → **확인하고** → 안 됐으면 다시

컴퓨터에게 시킬 때 제일 중요한 건 "됐는지 물어보는 것"이다.

### 5. "안 돼요"는 아직 질문이 아니다

오늘 세 가지를 고쳤는데, 처음 증상의 진짜 원인은 그중 하나도 아니었다.
**부른 방과 듣는 방이 달랐던 것뿐이다.**

"안 된다"는 말에서 바로 고치기 시작하면 이렇게 된다.
먼저 물어야 할 건 이거다. **어디서, 언제, 어떻게 불렀나요?**

고장을 찾기 전에 **어디서 고장났는지**를 찾아야 한다. 오늘 내가 순서를 바꿔 썼다.
