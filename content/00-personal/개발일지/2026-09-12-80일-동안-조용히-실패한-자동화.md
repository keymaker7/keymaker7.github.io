# 80일 동안 조용히 실패한 자동화

"지금 전체 상황 리스트업 해봐"라는 한 마디로 시작한 날이다.
기억으로 쓰지 않고 직접 재기로 했고, 그래서 **조용히 죽어 있던 것 네 개**가 나왔다.

## 🎯 목표

돌아간다고 믿고 있는 것들을 실제로 재서 목록으로 만든다.

## ✅ 정상이었던 것

먼저 멀쩡한 쪽. 봇 10기 전원 가동, 배포한 앱 9개 중 8개가 HTTP 200,
나머지 하나는 일부러 재운 것이라 503이 정상이다. 디스크도 전날 정리 효과가 유지되고 있었다.

측정 방법은 이렇게 갈랐다.

- 봇 — 프로세스 목록
- 웹앱 — HTTP 응답코드
- 자동화 — launchd 상태와 **산출물 날짜 대조**

세 번째가 이 글의 주제다.

## 💀 1. 이메일 자동화 — 80일째 죽어 있었다

받은 메일을 정리해 노트로 쌓는 자동화가 있다. 노트 폴더의 마지막 파일이 **6월 24일**이었다.
그날 이후 한 통도 들어오지 않았다.

원인은 단순했다.

```
imaplib.IMAP4.error: [AUTHENTICATIONFAILED] Invalid credentials
```

메일 앱 비밀번호가 만료됐거나 취소된 것이다. 이 에러가 **925번** 찍혀 있었다.

여기가 핵심이다. **2시간마다 실패를 반복하면서 80일 동안 아무도 몰랐다.**

왜 몰랐나. 감시가 "프로세스가 살아 있나"를 보고 있었기 때문이다.
프로세스는 멀쩡히 살아 있었다. 살아서 2시간마다 실패했다.

봐야 할 것은 **"산출물이 늘고 있나"**였다. 노트 폴더에 6월 24일 이후 파일이 하나도 없다는 것은
첫날에도 알 수 있었다. 아무도 그 폴더를 안 봤을 뿐이다.

### 게다가 2중 장애였다

고장이 두 개 겹쳐 있었다. 하나는 메일 분류를 맡은 쪽이 로그아웃된 것이고
(이것 때문에 만 이천 건이 버려졌다), 다른 하나가 위의 비밀번호다.

앞의 것은 **다른 작업을 하다가 우연히 복구돼 있었다.** 9월 초 자격증명을 정리하면서 같이 풀린 것이다.

2중 장애가 고약한 이유는 이거다. **하나를 고쳐도 여전히 안 되니까 "고쳤는데 안 되네"가 된다.**
그러면 방금 고친 것이 원인이 아니었다고 생각하고 엉뚱한 데를 판다.
두 개를 각각 확인해 나눠 적은 것이 이날의 제대로 한 일이었다.

## 🔇 2·3·4. 나머지 세 개도 같은 유형이었다

- **작업 결과함이 한 달째 끊겨 있었다.** 결과를 넣는 폴더가 이미 삭제된 클라우드 폴더를
  가리키고 있었다. 폴더를 만들려고만 해도 실패한다. 그 뒤 과제 결과가 어디에도 안 남았을 수 있다.
- **개발일지가 7일 비어 있었다.** 규칙 개편, 플러그인 검토가 기록되지 않았다.
- **이름 마스킹 명단에 3명만 등록돼 있었다.** 24명 기준이면 21명이 안 걸린다.
  (전화번호·주민번호 차단은 이름과 무관하게 작동 중이었다.)

네 개 다 **조용히 죽고, 산출물 폴더만 보면 즉시 드러나는 것들**이었다.

## 🤦 오보를 하나 냈다 — 그리고 3분 만에 정정했다

실측 중에 "세션 자동 기록이 6일째 멈춰 있다"를 먼저 올렸다. **틀렸다.**

그 로그는 **실패했을 때만 쓰이는 파일**이었다. 잘 돌고 있으면 아무것도 안 쓰니까 날짜가 안 바뀐다.
멈춘 날짜를 "죽었다"로 읽은 것이다. 실제로는 정상이었고, 커밋 기록을 보니 그날도 두 번 돌았다.

### 실패 전용 로그는 양방향으로 오진한다

```
정상 동작 중   → 로그 안 쓰임 → mtime 정지 → "죽었다"로 오진 ← 이날의 오보
작업 자체 정지 → 실패도 안 함 → mtime 정지 → 언제 죽었는지 모름
```

**로그의 mtime은 정상과 완전 정지를 구분하지 못한다.** 판정은 산출물 쪽에서 해야 한다.

그리고 이 오보는 애초에 낼 필요가 없었다. "2~3분 걸린다"고 말한 직후에 중간 소견을 내보낸 것이다.
재촉이 있었지만, 재촉에 답할 문장은 "확인 중입니다" 한 줄로 충분했다.
**실측 중이라고 말했으면 실측이 끝난 뒤에 말한다.**

## 🔑 그리고 가장 위험했던 한 마디

이날 아침 "밀린 메시지 없습니다"라고 답한 4분 뒤에 **11일 묵은 과제**가 나왔다.

이유는 위의 ②번 고장이다. 밀린 과제를 쌓아 두는 결과함이 끊겨 있었다.
**볼 수단이 없는 상태에서 "없다"고 답한 것이다.**

이게 이날 배운 것 중 가장 오래 남을 것 같다.
볼 수 없을 때의 정답은 "없습니다"가 아니라 **"못 읽습니다"**다.

## 🛠️ 그래서 바꿀 것

### 감시를 산출물 기준으로

```bash
# 6시간 안에 새 산출물이 없으면 경고
[ -z "$(find "$OUT_DIR" -type f -newermt '-6 hours' -print -quit)" ] \
  && echo "WARN: $OUT_DIR 정지"
```

이메일·기록 수확기·백업 세 갈래에 각각 걸면 80일 방치는 첫날 잡힌다.

### 큐를 못 읽으면 "없다"고 답하지 않기

```bash
[ -d "$QUEUE_DIR" ] || echo "큐 경로 끊김 — '밀린 것 없음' 답변 금지"
```

### 사용자가 해야 할 일은 다음 날 한 번 더 알리기

이게 이 글의 뒷맛이다. **닷새 뒤에 다시 재봤더니 이메일 자동화는 여전히 죽어 있었다.**
자동 작업은 등록돼 있고 마지막 종료 코드는 1(실패). 노트 폴더 마지막 파일도 그대로 6월 24일이다.

비밀번호 재발급은 계정 주인만 할 수 있는 일이라 스크립트까지 만들어 넘겼는데,
**넘긴 뒤 다시 알리지 않았다.** 80일 방치를 찾아낸 보고서가 그 뒤 닷새를 또 방치했다.

**발견이 복구는 아니다.**

## 🧾 정리

1. **프로세스가 살아 있는지 보는 감시는 조용한 실패를 못 잡는다.** 산출물이 늘고 있는지를 봐야 한다.
2. **실패 전용 로그의 mtime으로 상태를 판정하면 양방향으로 오진한다.**
3. **볼 수단이 없을 때의 답은 "없습니다"가 아니라 "못 읽습니다"다.**
4. **사용자 손이 필요한 항목은 넘긴 뒤 재알림까지가 한 세트다.** 안 하면 닷새가 그냥 간다.
