# 심링크 9개가 실파일 1개였다

여러 AI 에이전트를 한 대의 맥에서 돌리는데, 얘들이 자꾸 로그아웃됐다.
하루 종일 파서 찾은 원인이 꽤 교과서적이라 남긴다.

## 🔢 증상

기동 시도 **193건 중 실패 54건(28%).** 그중 `Not logged in` 이 32건.
간헐적이고, 재시작하면 또 잘 되고, 그러다 또 죽었다.

## 🕵️ 원인

에이전트마다 자격증명 파일 경로가 따로 있고, 전부 심링크로 한 곳을 가리키고 있었다.
그리고 감시 스크립트가 **"각 경로에 cp"** 로 자격증명을 배포하고 있었다.

```
9개 경로  →  전부 심링크  →  실파일은 단 1개
                              ↓
        "9곳에 배포" = 같은 파일을 9회 truncate + write
                              ↓
        그 사이에 읽는 프로세스는 빈 파일 또는 부분 JSON 을 본다
```

**배포가 아니라 자해였다.** 14개 프로세스가 그 파일을 수시로 읽고 있었으니
누군가는 반드시 잘린 순간에 걸린다.

### 그리고 `>` 가 심링크에 하는 일

이게 핵심이다. 다시 적어둔다.

```bash
echo "$data" > "$link"
# link 를 따라가 실파일을 0바이트로 자른 뒤 채운다
# 자르기와 채우기 사이에 읽으면 빈 내용을 본다
```

배포 스크립트를 짤 때 **대상이 심링크인지 실파일인지**부터 봐야 한다.

## 🔨 고친 것 셋

### 1. 실파일을 외장에서 내장으로

실파일이 exFAT 외장 디스크에 있었다. 여기서 **보너스 결함**이 하나 더 나왔다.

```bash
chmod 600 "$creds"   # 성공은 한다. 그런데 안 먹는다.
```

exFAT가 `noowners` 로 마운트돼 있으면 **권한이 마운트 옵션으로 합성**되기 때문에
`chmod` 이 무의미하다. 자격증명 파일이 사실상 무보호 상태였다.

> ⚠️ `chmod` 성공 ≠ 권한 적용. 걸고 나서 반드시 다시 읽어라.
> ```bash
> chmod 600 "$f" && stat -f '%Sp %N' "$f"
> mount | grep "$(df "$f" | awk 'NR==2{print $1}')"   # noowners 여부
> ```

실파일을 내장 APFS로 옮기고 심링크를 전부 재연결했다. 원자성 문제와 권한 문제가 함께 사라졌다.

### 2. 단일 기록자(single writer)로 바꿨다

```
① 고유 경로로 접어서 1회만 기록      (9회 → 1회)
② 같은 디렉터리 임시파일 + mv 로 교체 (truncate 창 제거)
③ 락으로 직렬화                       (동시 기록 차단)
④ 내용이 같으면 아예 안 씀            (불필요한 쓰기 0)
```

②가 중요하다. **같은 파일시스템 안의 임시파일에 다 쓰고 `mv` 로 갈아끼우면**
읽는 쪽은 옛 파일이나 새 파일 중 하나를 보지, 잘린 파일을 볼 일이 없다.

### 3. macOS에는 `flock` 이 없다

```
flock        바이너리 없음
python fcntl 자식 프로세스가 끝나면 락이 풀림 → 셸 스크립트 용도로 못 씀
```

그래서 **`mkdir` 의 원자성**을 썼다. 같은 이름의 디렉터리는 하나만 만들어진다.

```bash
if mkdir "$LOCK_D" 2>/dev/null; then
    echo "$$" > "$LOCK_D/pid"      # 내가 잡았다
fi
```

죽은 프로세스가 남긴 락을 회수하는 로직도 필요한데, **여기서 버그가 하나 더 나왔다.**

```bash
mt=$(stat -f %m "$LOCK_D" 2>/dev/null || echo 0)   # ❌ 이 폴백이 문제
age=$(( $(date +%s) - mt ))                         # age = 약 17억
[ "$age" -gt 300 ] && rm -rf "$LOCK_D"              # 항상 참 → 살아있는 락을 뜯음
```

`stat` 이 실패하면 `0` 이 들어가고, 그러면 나이가 현재 epoch가 되어
**살아 있는 락을 강제로 회수**해 버린다. 락이 없는 것만 못하다.

> 폴백 기본값이 조용히 비교식을 참으로 만드는 패턴은 락에서 특히 위험하다.
> 지금은 `stat` 이 실패하면 "락이 방금 사라졌다"로 보고 나이 판정을 아예 하지 않는다.

## 💣 제일 아픈 대목 — 고쳤는데 안 고쳐졌다

감시 스크립트를 원자적 교체로 고쳤다. 보고도 했다. 그런데 **다른 스크립트에**
이 한 줄이 그대로 남아 있었다.

```bash
echo "$keychain_creds" > "$creds_file"    # 네 번째 기록자
```

그리고 **그날 밤 실제로 이 줄이 공유 파일을 갈아엎었다.** 시각까지 로그에 찍혔다.

고친 사람은 자기가 고친 파일만 봤다. **같은 리소스에 쓰는 경로를 전수 조사하지 않았다.**

> 공유 자원을 만지는 수정의 완료 조건은
> "이 파일을 고쳤다"가 아니라 **"이 리소스에 쓰는 모든 경로를 세었다"** 다.
>
> ```bash
> grep -rn "credentials.json" <경로> --include="*.sh" \
>   | grep -E ">|cp |mv |tee |install "
> ```

## 🧯 덤 — "앱이 죽었나?" 는 대개 백엔드가 잠든 것

같은 날 오후, 배포해둔 강의용 웹앱이 죽었다는 얘기가 나왔다.

```
프론트(호스팅)   ✅ 200 OK, 화면도 정상
백엔드(DB)       ❌ INACTIVE — 무료 플랜 비활동 일시정지
```

**프론트가 200을 주기 때문에 겉보기로는 멀쩡하다.**
관리 API로 restore 호출했고 `INACTIVE → COMING_UP → ACTIVE_HEALTHY` 까지 **3분**,
비용 0원, 데이터 그대로였다.

배포해두고 안 쓰는 프로젝트는 주기적으로 이 상태가 된다.
"살아 있나?"를 사람이 물어봐야 아는 구조라면, 그건 구조 문제다.

## 💡 정리

1. **`>` 는 심링크를 따라가 실파일을 자른다.** 배포 대상이 심링크인지부터 확인.
2. **파일 교체는 같은 디렉터리 임시파일 + `mv`.** 읽는 쪽이 잘린 파일을 볼 일이 없어진다.
3. **`chmod` 성공과 권한 적용은 다르다.** `noowners` 마운트에서는 특히.
4. **macOS 셸 락은 `mkdir` 원자성으로.** `flock` 없고 `fcntl` 은 이 용도에 못 쓴다.
5. **폴백 기본값이 비교식을 참으로 만들지 않는지 본다.** 락에서는 치명적이다.
6. **공유 자원을 고쳤으면 쓰는 경로를 전수 조사한다.** 기록자는 한 명 더 숨어 있다.

## 📋 선임 리뷰 — 이날의 나에게

### 잘한 것
**증상이 아니라 구조를 고쳤다.** 아홉 개가 각자 로그인을 잃는 문제를 하나씩 다시 로그인시켜 덮지 않고,
공유해야 할 것이 사본으로 흩어져 있던 구조를 바로잡았다. **그 수정은 20일 뒤에도 그대로 살아 있다.**

### 반복된 나쁜 패턴
1. **낡은 열쇠를 지우지 않고 남겨뒀다.** 삭제 승인을 기다리다 그대로 잊었고, 보름 뒤 다른 설정 파일에서 또 하나가 발견됐다. 그것도 **지우지 않고 가려두기만** 했다. 무효한 열쇠는 지워야 한다 — 남아 있으면 다음 사람이 그게 유효한 줄 안다.
2. **점검 담당을 사람에게 맡기고 결과를 받지 않았다.** "24시간 지켜보고 0건인지 확인"을 넘겨놓고 그 결과를 확인하지 않았다.

### 20일 뒤에 확인한 것 — 그리고 더 나쁜 발견
그 오류는 실제로 사라졌다. 그런데 이유가 좋은 쪽이 아니었다.

**열쇠를 자동으로 갱신하던 장치가 닷새 반 전부터 죽어 있었다.**
마지막 성공 이후 62번 연속 실패했고, 실패 이유는 한 줄이다 —
프로그램 위치가 바뀌었는데 스크립트가 옛 경로를 그대로 부르고 있었다.

오류가 사라진 건 문제가 고쳐져서가 아니라 **지켜보던 장치가 먼저 죽어서였다.**

이번 달 내내 반복된 주제가 여기서 가장 선명하다.
**"조용해졌다"는 좋은 신호가 아니다.** 조용한 이유를 확인해야 한다.
그러려면 점검 장치 자신이 살아 있는지 보는 장치가 하나 더 필요하다.

### 남아 있는 부채
- 무효 열쇠가 지워지지 않고 가려진 채 남아 있음
- 자동 갱신 장치가 닷새 반째 실패 중 — 경로 한 줄 문제

## 🔎 스무 날 뒤에 덧붙임 — 구조는 버텼고, 돌보는 장치가 죽었다

앞에서 적은 발견(자동 갱신이 닷새 반 동안 죽어 있던 것)은 그 뒤 고쳐졌다.
프로그램 위치를 옛 경로로 부르던 줄을 바꿨고, 만료 시각을 읽는 경로도 정정했다.
만료 45분 전에 미리 갱신하는 동작도 새로 들어갔다. 실제 성공 실행 한 번만 남았다.

그리고 여기서 이 글의 진짜 교훈이 보인다.

- **구조를 고친 것은 오래 살았다.** 흩어진 사본을 하나로 묶은 이 수정은 **스무 날 뒤에도 열 군데 전부 그대로**다.
- **그 구조를 돌보는 장치는 조용히 죽었다.** 닷새 반 동안 62번 연속 실패했고, 아무도 몰랐다.

고쳐놓은 구조는 스스로 버틴다. 그런데 **그 구조를 유지해주는 자동화는 감시가 없으면 죽는다.**
그리고 그게 죽으면, 죽었다는 사실조차 조용하다 — 오히려 오류가 사라져서 좋아진 것처럼 보인다.

그래서 다음 한 줄이 필요하다.
**점검 장치의 마지막 성공 시각을 보는 항목**을 정기 점검에 넣는다.
"마지막 성공이 네 시간을 넘었으면 알린다" 정도면 충분하다.

### 검증 결과 — 그리고 내가 틀린 부분

두 시간 뒤 실제 실행 결과가 나왔다. **성공이다.** 닷새 반 만의 첫 성공이었고 경로 문제는 끝났다.

그런데 같은 실행에서 **경고 하나가 그대로 찍혔다.** 만료 시각을 읽지 못한다는 경고다.
나는 그 직전에 "그건 이미 고쳐졌다"고 판단했는데, **틀렸다.**

원인은 이랬다. 나는 자격증명 파일 하나를 열어 "이 경로로 읽으면 잘 읽힌다"고 확인했다.
그런데 **스크립트가 읽는 파일은 다른 파일이었다.** 그 파일에는 키는 있지만 **값이 0**이다.

그래서 만료 45분 전에 미리 갱신하는 장치는 여전히 동작하지 않는다 —
**만료된 뒤에야 움직인다.** 이건 따로 넘겼다.

**교훈이 하나 더 늘었다.** "같은 방식으로 읽어보니 성공했다"는 검증은 틀릴 수 있다.
**그 프로그램이 실제로 읽는 대상**을 그 프로그램에서 확인해야 한다.

앞에서 "확인할 수 있는 문장으로 적어라"라고 썼는데, 그 다음 단계는 이것이다 —
**같은 대상을 확인하라.**
