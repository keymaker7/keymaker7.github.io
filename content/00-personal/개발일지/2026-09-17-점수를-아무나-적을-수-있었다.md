# 점수를 아무나 적을 수 있었다

"내 블로그에 비밀번호나 개인번호 같은 게 남아 있나" 확인해 달라는 요청으로 시작했다.
블로그는 깨끗했다. 그런데 점검 범위를 앱까지 넓히자 얘기가 달라졌다.

이 글에 적는 구멍은 **전부 고쳐서 배포까지 끝낸 것들이다.** 지금 열려 있는 문제는 적지 않는다.

## 🔍 1. 블로그는 깨끗했다

먼저 블로그 저장소부터 봤다. 글 360개와 과거 커밋 1706개를 전부 훑었다.
이미 지운 내용도 커밋 기록에는 남으니까, 현재 파일만 보면 안 된다.

```bash
# 지금 파일이 아니라 "지나간 모든 커밋"에서 찾는다
git log --all -p | grep -E 'sk-[A-Za-z0-9]{20,}|BEGIN .*PRIVATE KEY'
```

API 키, 비밀번호, 전화번호, 주민번호, 계좌번호 — 0건이었다.
이메일 세 건이 잡혔는데 블로그 틀(Quartz)을 만든 외국 개발자 것이었다.

대신 다른 게 걸렸다. 개발일지에 **"어느 앱에 접근 통제가 없다"고 그대로 적어둔 문장**이 있었다.
블로그는 공개다. 금고 비밀번호는 안 적었지만 "뒷문이 열려 있다"는 메모를 문에 붙여둔 셈이다.
교훈은 남기고 어느 앱인지는 지웠다.

## 🧯 2. 진짜 구멍은 앱에 있었다

앱 13개를 훑었다. 라이브 화면을 받아 안에 들어 있는 스크립트까지 전부 뒤졌다.

**키 유출은 0건이었다.** 모든 열쇠가 서버 쪽 환경변수에 있었고 화면으로 내려온 게 없었다.
이건 다행이었다.

문제는 다른 종류였다. 어떤 앱이 어떻게 열려 있었는지는 여기 적지 않는다.
**전부 고쳐서 배포까지 끝냈지만, 공개된 글에 남길 내용은 아니다.**

보안을 보러 갔다가 덤으로 실제 고장도 하나 주웠다.
어떤 버튼이 눌러도 무조건 실패하는 상태였는데, 아무도 모르고 있었다.

## 🧪 3. "고쳤습니다"가 틀렸다

여기가 오늘의 핵심이다.

구현을 맡긴 쪽에서 "테스트 통과, 권한 없으면 401·403을 돌려줍니다"라고 보고했다.
믿고 넘어갈 뻔했는데, 검증을 **다른 담당에게 따로** 맡긴 게 걸러냈다.

실제 코드는 거부할 때도 **성공(200)을 돌려주고 있었다.**

```js
// 이렇게 쓰면 "실패"라고 적어 보내면서 상태는 200(성공)이다
return res.json({ ok: false, error: 'NEED_TOKEN' });

// 상태 코드까지 붙여야 진짜 거부다
return res.status(401).json({ ok: false, error: 'NEED_TOKEN' });
```

테스트는 오류 이름만 확인하고 있었다. 숫자는 안 보고 있었던 것이다.
**"검사를 통과했다"는 말은 "무엇을 검사했는지"를 확인하기 전까지 아무 뜻이 없다.**

그 다음 검사 항목이 20개에서 13개로 줄어든 것도 발견했다.
검사를 줄이면 통과는 쉬워진다. 되돌리라고 했다.

## 💀 4. 배포했더니, 저장이 원래부터 안 되고 있었다

고친 걸 올리고 실제로 찔러봤다. 문이 잘 잠긴 건 확인됐다.
그런데 데이터를 읽고 쓰는 요청이 전부 실패했다. 데이터베이스에 닿지를 못했다.

내가 방금 올린 것 때문일까? 이게 제일 중요한 질문이었다.
그래서 **고치기 전 코드를 잠깐 다시 올려서 똑같이 찔러봤다.**

```bash
git worktree add /tmp/기준점 <고치기-전-커밋>   # 옛 코드를 따로 꺼내고
cd /tmp/기준점 && vercel --prod                  # 잠깐 올려서
curl -X POST .../api/db -d '{"action":"..."}'    # 같은 요청을 찍어본다
```

옛 코드도 똑같이 실패했다. **내 변경 탓이 아니라, 원래부터 죽어 있었다.**

즉 아이들 독서 기록이 각자 기기 안에만 쌓이고 있었고, 교사 화면은 계속 비어 있었을 것이다.
그런데 화면은 멀쩡해 보였다. 저장 실패를 코드가 조용히 삼키고 있었기 때문이다.

```js
// 실패를 이렇게 삼키면 아무도 모른다
save().catch(() => {});

// 최소한 화면에는 보이게
save().then(r => r.ok ? 숨김() : 경고표시()).catch(경고표시);
```

역설적이게도, 그래서 "반 명단이 보인다"는 구멍은 실제 피해가 없었다. 볼 데이터가 없었으니까.

## 🔌 5. 끊어진 줄을 다시 잇는 데 여덟 번 걸렸다

원인은 알았으니 붙이기만 하면 되는 줄 알았다. 그런데 여기서 제일 오래 걸렸다.

열쇠를 새로 넣어달라고 부탁하고, 확인하고, 안 됐다고 말하고, 다시 부탁하고. 이걸 여덟 번 했다.
문제는 열쇠가 아니라 **내 안내가 틀렸다는 것**이었다.

- 나는 데이터베이스를 주소로 불렀는데, 화면 목록에는 **별명으로 떠 있었다.** "그런 거 없는데요"가 나온 이유다
- 열쇠 복사하는 칸에 **「읽기 전용」 체크가 켜져 있었다.** 그 열쇠로는 저장이 안 된다
- 설정 화면의 「등록일」이 **값을 바꿔도 안 바뀐다.** 나는 이걸 보고 "저장이 안 됐다"고 세 번 잘못 말했다

마지막 것이 특히 나빴다. 근거가 틀렸는데 결론이 확신에 차 있었다.

그래서 추측을 그만두고 **서버에 잠깐 계측기를 달았다.**

```js
// 값은 절대 돌려주지 않는다. 길이와 주소만 확인한다
if (action === '_envcheck') {
  return res.json({ urlHost: new URL(U).host, tokenLen: String(T || '').length });
}
```

이걸로 "서버가 실제로 뭘 들고 있는지"가 눈에 보이게 됐다.
다만 여기서도 한 번 더 틀렸다. 길이가 그대로라서 "안 바뀌었다"고 했는데,
**새 열쇠도 우연히 같은 길이(62자)였다.** 길이는 애초에 판별 근거가 못 됐던 것이다.

결국 판정은 하나로 끝났다. **실제로 요청을 보내보는 것.**

## 📚 6. 숫자는 맞았는데, 뜻을 잘못 읽었다

붙이고 나서 제일 궁금한 건 하나였다. 8월 기록이 남아 있을까.

누가 무슨 책을 읽었는지까지 볼 이유는 없으니, **개수만 돌려주는 임시 장치**를 만들어 세어봤다.

```js
// 이름도 책 제목도 안 꺼낸다. 몇 개인지만 센다
for (const key of keys) if (isStudentKey(key)) students++;
return res.json({ classCount, students });
```

반 29개, 학생 기록 9건, 책 10권. 날짜도 8월 7일부터 30일까지였다.
나는 "아이들 기록이 살아남았다"고 보고했다. **그리고 그건 틀린 말이었다.**

나중에 정리하면서 반 이름을 봤더니 이랬다.
「보안테스트반」 「독서왕검증반」 「진행률검증」 「추천피드검증」 「라운지테스트」.

학생이 있는 반 6개 중 5개가 내가 개발하며 만든 연습용이었다.
수업용으로 보이는 「4학년 1반」은 딱 하나였는데, 책 기록이 0권이었다.

살아 있던 건 **연습 데이터**였다. 진짜 아이들 기록은 애초에 쌓인 적이 없었다.
저장이 몇 주째 죽어 있었으니 당연한 결과였는데, 나는 숫자만 보고 반대로 읽었다.

## 🎯 7. 점수를 서버가 매기게 바꿨다

순위표를 쓰는 게임은 구조부터 다시 봐야 했다.
예전 방식은 게임이 끝나면 **화면이 자기 점수를 계산해서 "나 1200점"이라고 서버에 알려주는** 방식이었다.
그 말을 서버가 그대로 믿고 적었다. 숫자를 바꿔 보내면 그대로 올라간다.

바꾼 구조는 이렇다.

1. 서버가 문제를 만든다. **정답은 화면으로 안 내려보낸다.**
2. 화면은 "몇 번을 골랐다"만 보낸다.
3. 서버가 문제를 내준 시각을 기억했다가, 답이 온 시각과의 차이로 속도 점수까지 직접 계산한다.
4. 점수는 서버 안에서만 쌓인다.

```js
// 문제를 내줄 때 정답(a)을 빼고 보낸다
const strip = q => ({ w: q.w, d: q.d, choices: q.choices });

// 채점도 서버가 한다. 화면이 보낸 점수는 쳐다보지도 않는다
const elapsed = Date.now() - session.shownAt;      // 내가 문제를 낸 뒤 얼마나 지났나
const correct = elapsed <= 제한시간 && choice === q.a;
session.score += correct ? 기본점수 + 속도보너스(elapsed) : 0;
```

옛 방식으로 9만 점을 올려봤다. 순위표에 한 명도 안 적혔다.

## 🚦 8. 잠가놨는데도, 무한히 두드릴 수 있었다

점검을 마치고 한 가지를 더 해봤다. **똑같은 요청을 스무 번 연속으로 보내보는 것.**

한쪽은 열두 번째에서 "조금 뒤에 다시 해줄래?" 하고 막았다.
다른 한쪽은 스무 번을 전부 받아줬다.

권한은 둘 다 제대로 잠겨 있었다. 남의 것을 보려 하면 거절당했다.
그런데 **거절당하는 횟수에 제한이 없으면, 계속 시도해볼 수 있다.**
자물쇠는 튼튼한데 열쇠를 몇 번이든 끼워볼 수 있는 상태였다.

그래서 접속한 곳마다 횟수를 세고, 넘으면 잠깐 쉬게 했다.

```js
// 누른 횟수를 세고, 창이 지나면 저절로 잊는다
async function tooMany(key, limit, windowSec) {
  try {
    const [n] = await redis([['INCR', `rl:${key}`]]);
    if (+n === 1) await redis([['EXPIRE', `rl:${key}`, String(windowSec)]]);
    return +n > limit;
  } catch (e) { return false; }   // 세는 쪽이 고장나면 수업을 막지 않는다
}
```

한도는 행동마다 다르게 줬다. 저장은 수업 중 자주 일어나니 넉넉하게,
새로 만드는 일은 드무니 빡빡하게. **보안 때문에 수업이 멈추면 그게 더 나쁘다.**

고치고 다시 스무 번을 보내봤다. 이번엔 중간에 막혔다.

## 🔎 9. 열쇠처럼 생겼다고 열쇠는 아니다

마지막으로 한 번 더 훑었다. 화면에 열쇠가 섞여 나오지 않는지 보는 일이다.

찾는 방법은 단순하다. 열쇠처럼 생긴 모양을 기계에게 찾게 한다.

```bash
# 긴 무작위 글자, 흔한 키 이름, 접속 주소 — 열쇠가 흘렀을 때 나오는 모양들
grep -ioE 'A[A-Za-z0-9_-]{50,}|[A-Z_]*API_KEY|[A-Z_]*TOKEN' 받아온화면.html
```

한 건이 걸렸다. 50자짜리 뒤죽박죽 글자. 심장이 한 번 내려앉았다.

열어보니 **3D 장면을 넣으려고 붙여둔 주소**였다. 주소 끝에 붙은 긴 글자가
열쇠와 똑같이 생겼을 뿐이었다. 공개돼도 아무 문제 없는 것이었다.

기계가 찾아주는 건 **"닮은 것"**이지 "위험한 것"이 아니다.
걸린 건 반드시 눈으로 한 번 봐야 한다. 안 그러면 없는 사고를 만들어낸다.
오늘 아침에 숫자만 보고 틀렸던 것과 같은 실수를 하마터면 또 할 뻔했다.

그리고 점검하느라 만든 연습용 자료를 전부 지웠다.
어떤 앱은 며칠 뒤 저절로 사라지지만, 어떤 앱은 지워주지 않으면 영영 남는다.
**치우는 것까지가 점검이다.**

## 👨‍🏫 오늘 코딩선배의 가르침

### 1. 점수는 "신고"가 아니라 "채점"이어야 한다

시험을 볼 때 학생이 자기 점수를 적어서 내면 어떻게 될까?
대부분은 정직하겠지만, 딱 한 명만 장난쳐도 등수가 전부 흔들린다.
**채점은 선생님이 해야 한다.** 컴퓨터도 똑같다.

- 나쁜 방법: 게임 화면이 "나 1200점!" 하고 서버에 알려준다
- 좋은 방법: 서버가 문제를 내고, 답을 받고, 서버가 점수를 센다

쉽게 말하면 **정답지를 학생 책상 위에 두지 않는 것**이다. 정답을 아예 안 보내주면 베낄 수가 없다.

### 2. "다 고쳤어요"는 확인하기 전까지 그냥 말이다

오늘 제일 크게 배운 것. 고쳤다는 보고를 받고 직접 열어보니 안 고쳐져 있었다.
심지어 "검사했다"는 검사도 엉뚱한 걸 보고 있었다.

**확인하는 사람은 만든 사람과 달라야 한다.** 내가 만든 건 내 눈에 잘 만든 것처럼 보인다.
숙제를 짝꿍과 바꿔 검사하는 것과 같은 이유다.

### 3. 조용한 실패가 제일 무섭다

이번에 제일 오래 방치돼 있던 문제는 **아무 표시도 없이 실패하던 저장**이었다.
화면은 멀쩡했다. 그래서 몇 주 동안 아무도 몰랐다.

```js
save().catch(() => {});   // 이 한 줄이 문제를 몇 주 숨겼다
```

에러가 뜨는 프로그램은 금방 고쳐진다. **아무 말 없이 안 되는 프로그램이 오래 간다.**
실패하면 반드시 티를 내게 만들자. 빨간 글씨 한 줄이면 충분하다.

### 4. 고장 원인을 가르는 법 — 옛것을 다시 돌려보기

"내가 방금 바꾼 것 때문인가?"가 헷갈릴 때가 있다.
그럴 땐 **바꾸기 전 상태로 되돌려서 똑같이 해보면 된다.**

- 옛것도 안 되면 → 내 탓이 아니다. 원래 고장나 있었다
- 옛것은 되면 → 내가 방금 깬 것이다

추측으로 한 시간 고민하는 것보다 3분 실험 한 번이 낫다.

### 5. 같은 안내를 세 번 반복했다면, 틀린 건 상대가 아니라 안내다

열쇠를 다시 넣어달라고 여덟 번 부탁했다. 매번 "안 됐습니다"라고 답했다.
그런데 진짜 원인은 내가 데이터베이스를 **다른 이름으로 부르고 있었던 것**이었다.

같은 말을 세 번째 반복하고 있다면 멈춰야 한다.
**"왜 안 하지"가 아니라 "내 설명의 어디가 안 보이지"로 질문을 바꾸는 것**이다.
결국 답을 준 건 상대가 보내준 화면 사진 한 장이었다.

### 6. 숫자를 세는 것과 뜻을 아는 것은 다르다

기록이 살아 있는지 보려고 **개수만 세는 장치**를 만들어 썼다.
남의 독서 기록을 다 열어보지 않아도 되니 좋은 방법이었다. 그건 지금도 맞다.

그런데 나는 "29개, 9건, 10권"만 보고 **"아이들 기록이 살아남았다"고 결론지었다.**
나중에 이름을 보니 대부분 「보안테스트반」 같은 연습용이었다. 숫자는 맞고 뜻은 틀렸다.

세는 것으로 충분한 질문이 있고, 한 개라도 열어봐야 아는 질문이 있다.
**"몇 개야?"와 "그게 뭐야?"는 다른 질문이다.** 나는 앞의 답으로 뒤의 답을 말해버렸다.

### 7. "잠갔나?"보다 "몇 번까지 되나?"

자물쇠가 튼튼한지만 보면 절반만 본 것이다.
**몇 번이든 시도할 수 있으면, 튼튼한 자물쇠도 언젠가 열린다.**

확인하는 법은 아주 단순하다. 같은 걸 스무 번 눌러보면 된다.
스무 번이 다 통과하면 제한이 없는 것이고, 중간에 막히면 있는 것이다.

비밀번호를 세 번 틀리면 잠기는 휴대폰과 같은 이야기다.
막는 것만큼 **몇 번까지 허락할지 정하는 것**도 보안이다.

### 8. 기계가 찾아준 것은 "닮은 것"이지 "위험한 것"이 아니다

열쇠가 새지 않았는지 찾을 때는 기계에게 맡기는 게 빠르다.
그런데 기계는 **모양만 본다.** 오늘도 열쇠처럼 생긴 글자가 하나 걸렸는데,
열어보니 그림을 불러오는 주소였다. 공개돼도 되는 것이었다.

반대 실수도 있다. 걸린 게 하나도 없다고 안전한 것도 아니다.
기계가 모르는 모양이면 그냥 지나간다.

**찾는 건 기계가, 판단은 사람이.** 걸린 건 반드시 하나씩 열어볼 것.
숫자만 보고 뜻을 단정하지 말라는 앞의 이야기와 같은 말이다.

### 9. 못 하는 건 못 한다고 말하기

무엇을 해도 완전히 막히지 않는 부분은 남는다.
"이제 안전합니다"라고 말하고 싶은 유혹이 있었지만, 그렇게 말하면 **안심하고 확인을 안 하게 된다.**

할 수 있는 것과 없는 것을 나눠서 말하는 게 진짜 안전이다.
담을 높였다고 말하는 것과, 아무도 못 넘는다고 말하는 것은 다르다.

## 📋 선임 리뷰 — 이날의 나에게

### 잘한 것
**검증에 걸렸을 때 배포를 세 번 연속 막았다.** "통과하지 못했습니다. 배포하지 않았습니다."
이 한 줄이 이날 가장 값지다. 아이들이 쓰는 앱에 로그인 불가와 조용한 저장 실패를 내보내지 않았다.

**지어내는 것을 구조로 막았다.** 인물 답변을 AI 생성이 아니라 자료 카드에서 고르게 했고,
카드에 없으면 「상상해서 답함」으로 표시한다. **모델을 믿는 대신 설계로 해결했다.**

**과장한 보고를 스스로 정정했다.** "옛 기록이 살아 있다"고 했던 것을 연습 데이터였다고 고쳐 적었다.

### 반복된 나쁜 패턴
1. **17일간 저장이 0건이었는데 아무도 몰랐다.** 앱 하나만 연결 주소가 안 바뀐 채 이전이 끝났고, 실패가 화면에 안 뜨는 구조였다. 경고는 이번에 넣었지만, **이전 작업의 사후 확인 목록이 없었다**는 문제는 그대로다.
2. **여덟 번의 교체 시도가 전부 헛수고였다.** 원인은 값이 아니라 작업하던 컴퓨터였다. 파일이 안 바뀐다는 신호를 1~2회차에 봤는데 방법만 바꿨다. **같은 패턴을 이틀 뒤에 또 반복했다.**
3. **길이로 같은지를 판단했다.** "62자니까 안 바뀐 것"은 틀렸다 — 새 값도 62자였다. 우연히 같아질 수 있는 지표를 판정 근거로 썼다.
4. **보안 내용을 올린 뒤에 지웠다.** 어느 앱이 어떻게 열려 있었는지가 한때 공개돼 있었다. 지웠지만 순서가 틀렸다 — **고친 것만 쓴다**는 규칙은 발행 전에 적용돼야 한다.
5. **권하기 전에 한도를 확인하지 않았다.** 데이터베이스 분리를 권했다가 무료 요금제 제한으로 취소했다. 확인 한 줄이면 됐던 것에 왕복 30분을 썼다.

### 다음에 똑같이 안 당하려면
- **"저장됐다"를 화면이 아니라 서버 응답으로 확인한다.** 주간 1회 저장 건수 확인을 점검 항목에 넣는다.
- **원격 편집을 부탁하기 전에 기기를 먼저 확인한다.** 파일 수정 시각을 1회차에 묻는다.
- **동일성 판단에 길이·개수를 쓰지 않는다.** 해시 앞 여섯 자리를 비교한다.
- **공개본은 "고친 것만" 필터를 발행 전에 통과시킨다.** 발행 후 삭제는 이미 늦다.
