# 새 AI 모델을 검증하는 법

해커톤에 나갔다가 떨어졌다. 그날 오후에 한 일이 오히려 더 남았다.

## 🤔 문제 — "이 모델 좋다던데, 좋은지 어떻게 알지"

새 모델이 나올 때마다 벤치마크 점수가 돌아다닌다.
그런데 그 점수는 **내 업무를 말해주지 않는다.**

그래서 기준을 하나로 바꿨다.

> **내가 정답지를 가진 과제를 던진다.**

마침 있었다. 만들어둔 체육 웹앱이 초등 5·6학년 체력측정 12종목의
측정 기준을 이미 구현하고 있었다. **그 데이터가 채점 기준표가 된다.**

## 📝 과제 설계 — 세 가지를 박아 넣었다

```
초등 5·6학년 체력측정 12종목의 측정 방법을 표로 정리해줘.
숫자가 들어가는 항목은 근거 문서·조항을 명시할 것.
모르면 «불확실»이라고 쓰고 지어내지 말 것.
```

각 문장이 채점 도구다.

| 요구 | 무엇을 재는가 |
|---|---|
| **표로 정리** | 항목 단위로 대조할 수 있게 된다 |
| **근거 문서·조항 명시** | 출처를 실제로 눌러볼 수 있다 |
| **모르면 «불확실»** | 환각 여부가 그대로 드러난다 |

## 📊 결과 — 12개 중 10 / 1 / 1

```
✅ 정확        10개
❌ 우리와 불일치  1개
⚪ 대조 불가     1개  ← 우리 정답지에 없던 걸 더 알고 있었다
```

맞춘 것들이 꽤 잘았다. 「분당 24회·3분」, 「발 간격 5cm 이하·2초 유지·2회」,
「무릎 90°·3초에 1회·2회 위반 시 종료」 같은 세부 수치까지 맞았다.

### 출처를 진짜로 가져왔다

붙여온 링크 4개를 **전부 눌러봤다. 전부 200으로 열린다.**
관련 규칙 조항 페이지와 별표 원문 파일까지 실재했다.

그리고 학교별로 실제 실시하는 종목은 지시대로 **«불확실»로 표시하고 멈췄다.**
지어내지 말라고 했더니 정말 안 지어냈다.

### ❗ 불일치 1건 — 여기가 제일 중요하다

악력 기록을 어떻게 채택하느냐에서 갈렸다.

```
우리 앱 :  좌·우 각각 높은 기록의 평균
모델    :  전체 최고 기록 하나
```

여기서 **"모델이 틀렸다"고 적고 싶은 유혹**이 온다. 내 앱이 기준표니까.

그런데 그렇게 안 썼다.

> 어느 쪽이 틀렸는지는 아직 모른다.
> **우리 앱이 틀렸을 가능성도 같은 무게로 있다.**
> 원문 별표를 열어봐야 결론이 난다.

**이건 모델 채점 건이 아니라 내 앱 점검 건으로 남았다.**
검증하려고 만든 기준표에서 오히려 내 쪽 버그 후보가 나온 셈이다.

> 쉽게 말하면 — 정답지를 들고 채점하다가, 정답지가 틀렸을 수도 있다는 걸 알게 됐다.
> 이게 검증을 제대로 했다는 신호다.

## 🔒 두 번째 과제 — 배포 중인 웹앱들 보안 감사

같은 모델에 두 번째 실제 업무를 붙였다.
배포 중인 웹앱 여러 개를 읽기 전용 샌드박스에서 훑게 했다.
파일 변경 없음, 외부 네트워크 요청 없음, 비밀값 미기재 조건.

### 그런데 결과를 그대로 쓰지 않았다

**보고서를 받고 나서 지적을 하나씩 코드로 대조했다.** 결과가 갈렸다.

| 지적 | 대조 결과 |
|---|---|
| 인증 기본값이 하드코딩돼 있다 | ✅ **사실** — 실제로 있었다 |
| 어떤 API가 인증 없이 열려 있다 | ⚠️ 사실이나 **설계상 의도된 트레이드오프** |
| 저장 후 검사라 경쟁 조건이 있다 | ❌ **과장** — 이미 원자적 처리 + 롤백이 들어 있었다 |
| 새 평문 자격증명 유출 | ✅ **0건** |

**세 번째 줄이 핵심이다.** 코드를 열어본 사람만 잡을 수 있는 과장이었다.

> **LLM 감사 보고서는 「지적 목록」이지 「판정」이 아니다.**
> 원문 대조 전에는 실행 지시로 쓰면 안 된다.

그래서 보고서 맨 위에 이 문장을 박아뒀다.

```
⚠️ 이 보고서는 1차 산출물이며, 아래 「재검증」 절이 그 위에 덧붙는 정정입니다.
   원문을 그대로 실행 지시로 쓰지 마십시오.
```

### 진짜 수확은 하나였다

여러 지적 중 실제로 급했던 건 **하드코딩된 인증 기본값** 하나였다.

```js
const secret = process.env.AUTH_SECRET || 'dev-insecure-fallback'   // ❌
```

개발 편의로 넣은 `||` 폴백이 그대로 배포돼 있었다.
환경변수가 빠진 배포에서는 **소스에 적힌 값으로 세션을 위조할 수 있다.**

```js
const secret = process.env.AUTH_SECRET
if (!secret) throw new Error('AUTH_SECRET 필수')                    // ✅
```

> **비밀값의 fallback 은 기본값이 아니라 거부여야 한다.**
> 안 뜨는 게 맞다. 뜨되 뚫린 채로 도는 것보다 낫다.
>
> 그리고 기본값이 실제로 쓰인 이력이 있으면
> **키 교체 + 기존 세션 무효화**까지가 한 작업이다. 고치기만 하면 위조 세션은 그대로 산다.

이날 밤부터 그 앱의 보안 작업이 시작됐다.

## 🧾 그리고 — 모른다고 적은 것들

감사 보고서 끝에 이걸 그대로 남겼다.

```
· Git 이 없는 저장소 3개  →  현재 파일만 확인, 커밋 이력 미확인
· 과거 커밋 본문 미열람   →  과거 자격증명 포함 여부 미확인
· 한 저장소는 pack 인덱스 경고로 이력 완전성 제한
```

**"검사했다"와 "검사 범위가 여기까지였다"는 다른 말이다.**
후자를 안 적으면 나중에 자기가 속는다.

## 💡 정리

1. **벤치마크 말고 내가 정답지를 가진 과제로 재라.** 숫자가 나온다.
2. 과제에 **「출처 명시」와 「모르면 불확실이라 쓸 것」**을 박아라. 그게 채점 도구다.
3. **출처 링크는 직접 눌러봐라.** 그럴듯한 URL과 열리는 URL은 다르다.
4. **내 기준표가 틀렸을 가능성을 열어둬라.** 불일치가 나왔을 때 진짜 수확은 그쪽일 수 있다.
5. **LLM 감사 결과는 원문 대조 전엔 지적 목록일 뿐이다.** 과장이 섞인다.
6. **비밀값에 `||` 폴백을 쓰지 마라.** 없으면 거부.
7. **검사 범위의 한계를 보고서에 적어라.** 모르는 걸 모른다고 쓴 보고서가 더 쓸모 있다.
